# RepoMoss --- Complete Project Plan

## Open-Weight AI Codebase Maintenance Agent

**Tagline:** *You build what's next. RepoMoss tends to what you've left
behind.*

**Project concept:** RepoMoss is a local-first AI agent that finds
small, neglected maintenance tasks in a software repository, proposes
and attempts low-risk fixes in an isolated Git worktree, runs approved
verification commands, and presents a transparent report for human
review.

------------------------------------------------------------------------

## 1. Project Summary

Software projects accumulate small chores: incomplete documentation,
TODOs, missing regression tests, stale configuration notes, and
straightforward maintenance issues. These tasks are easy to postpone
because they are rarely urgent, yet they gradually make a codebase
harder to maintain.

RepoMoss aims to handle these chores in a controlled background
workflow. A developer selects a repository and configures what RepoMoss
may inspect, which commands it may run, and which kinds of changes it
may attempt. The agent scans the repository, prioritizes suitable tasks,
uses a local open-weight model to plan a bounded change, works in an
isolated Git worktree, runs allowed tests, and produces a report
containing the actual diff and verification results.

**Core principle:** A generated patch is not automatically a successful
fix. RepoMoss must report what it attempted, what it verified, and what
still requires human review.

### The problem

Developers often postpone maintenance work because it interrupts feature
development. Conventional AI coding assistants generally respond to a
direct request; RepoMoss instead focuses on discovering and processing
small maintenance tasks with minimal prompting.

### The proposed solution

A local-first maintenance loop:

1.  Inspect a user-selected repository.
2.  Discover candidate maintenance tasks.
3.  Prioritize tasks using deterministic rules and local-model
    assistance.
4.  Check the task against explicit safety policies.
5.  Attempt one bounded task in an isolated worktree.
6.  Run approved verification commands.
7.  Save the patch, logs, and results.
8.  Present a concise maintenance report for review.

### Target users

-   Individual developers with side projects.
-   Open-source maintainers.
-   Students maintaining coursework and hackathon repositories.
-   Small teams that want a transparent, low-cost local maintenance
    helper.

------------------------------------------------------------------------

## 2. Goals and Non-Goals

### MVP goals

-   Run the core workflow locally.
-   Use an open-weight model through Ollama.
-   Inspect a user-selected Git repository.
-   Detect a small, clearly defined set of maintenance opportunities.
-   Generate a prioritized task list with reasons.
-   Attempt safe, bounded fixes in an isolated Git worktree.
-   Run only explicitly approved commands.
-   Record diffs, logs, test outcomes, and failures.
-   Require human approval before changes are merged or applied to the
    main working tree.
-   Provide a dashboard and a Markdown maintenance report.

### Non-goals for the first version

-   Fully autonomous merging or deployment.
-   Automatically upgrading arbitrary dependencies.
-   Running unrestricted shell commands generated by a model.
-   Guaranteeing that every model-generated patch is correct.
-   Supporting every programming language and build system.
-   Uploading private repository content to a remote AI service.
-   Building a general-purpose coding chatbot.
-   Automatically modifying the user's original working tree.

Keep the first release narrow. A dependable agent that completes one or
two maintenance task types is preferable to a broad agent that
frequently fails.

------------------------------------------------------------------------

## 3. Product Principles

1.  **Local-first:** repository contents and model inference stay on the
    user's machine by default.
2.  **Small steps:** attempt one bounded task at a time.
3.  **Least privilege:** give the agent access only to the selected
    repository and approved commands.
4.  **Isolation:** work in a dedicated Git worktree or branch.
5.  **Verification over confidence:** use actual command results, not
    model assertions, to report success.
6.  **Human control:** the user decides whether to keep, discard, or
    manually apply a patch.
7.  **Transparency:** every task has a reason, status, diff, command
    log, and result.
8.  **Graceful failure:** preserve failed attempts and explain what went
    wrong instead of repeatedly retrying without limits.
9.  **No fabricated outcomes:** distinguish generated, applied, tested,
    and human-approved changes.
10. **Configurable behavior:** users can adjust allowed task categories,
    model choice, budgets, and verification commands.

## 4. MVP Feature Set

### 4.1 Repository onboarding

The user selects a local Git repository. RepoMoss checks:

-   Whether the path exists and is a Git repository.
-   Whether Git is installed.
-   Whether the repository has uncommitted changes.
-   The current branch and commit.
-   Whether a supported project manifest or test configuration is
    present.
-   Whether the repository is within configured file and size limits.

The user must explicitly confirm the repository path and the commands
RepoMoss may run.

### 4.2 Repository scanner

Start with predictable, low-risk checks:

-   Find TODO, FIXME, and XXX comments.
-   Identify README sections that appear incomplete relative to the
    project structure.
-   Detect source files with no nearby tests, where the project layout
    makes this check meaningful.
-   Identify broken local links in Markdown.
-   Check for missing documentation of environment variables referenced
    by configuration or code.
-   Detect obvious duplicate or stale documentation files using
    deterministic rules.

Do not treat every finding as a defect. Each finding should include
evidence, file paths, a short explanation, and confidence or priority.

### 4.3 Task prioritization

Use a hybrid approach:

-   **Deterministic scoring:** risk, scope, affected files, task
    category, and availability of verification.
-   **Local model:** summarize the finding, propose a bounded plan, and
    explain why it may be useful.
-   **Policy gate:** reject unsupported or unsafe tasks before
    execution.

A suggested score can combine user-defined weights for impact,
confidence, reversibility, and verification availability. The score is a
prioritization aid, not proof that a task is correct.

### 4.4 Local AI planner

Use an open-weight model served through Ollama. Gemma 3 4B is a
candidate starting point, but model suitability depends on the available
hardware and the quality of generated patches.

The model should return structured task plans containing:

-   Task identifier.
-   Problem summary.
-   Evidence and relevant paths.
-   Proposed change.
-   Expected files affected.
-   Verification plan.
-   Risk classification.
-   Reasons the task should be deferred or rejected.

Validate model output against a schema. Treat repository content as
untrusted data, not instructions. Repository files may contain
prompt-injection text; system policies must take precedence over content
found in the repository.

### 4.5 Safe execution

For the MVP:

-   Create a dedicated worktree from a known commit.
-   Never overwrite the user's existing changes.
-   Limit the number of files and patch size.
-   Restrict write access to the worktree.
-   Allow only configured verification commands.
-   Set timeouts and resource limits where possible.
-   Capture stdout, stderr, exit status, and duration.
-   Stop after a bounded number of attempts.
-   Do not allow model-generated commands to run automatically.
-   Do not permit network access or deployment commands by default.
-   Require explicit approval for any operation that changes the main
    working tree, merges a branch, or pushes to a remote.

A worktree provides useful isolation from the original working tree, but
it is not a complete security sandbox. Use OS-level isolation or a
container for untrusted code and commands.

### 4.6 Verification engine

Each task should have an explicit verification plan.

Examples:

-   Documentation change: validate Markdown links and confirm referenced
    paths exist.
-   Test addition: run the specific test command approved for the
    repository.
-   Configuration documentation: compare documented variable names with
    the relevant configuration sources.
-   Simple code maintenance: run targeted tests, then broader tests if
    configured and feasible.

Verification statuses:

-   `passed`: configured checks completed successfully.
-   `failed`: one or more checks failed.
-   `not_run`: no suitable verification was configured.
-   `blocked`: execution was prevented by a policy or environment
    limitation.
-   `needs_review`: checks passed, but human judgment is still required.

A passing test suite does not prove that a change is correct. Report the
scope of the checks accurately.

### 4.7 Maintenance report

Each run should produce a dashboard summary and a Markdown report with:

-   Repository and base commit.
-   Run start/end time.
-   Tasks discovered and selected.
-   Why each task was prioritized.
-   Files changed.
-   Patch or diff.
-   Commands executed.
-   Test results and exit codes.
-   Failures and limitations.
-   Model name and relevant configuration.
-   Human review status.
-   Suggested next action.

Example statuses should be grounded in actual execution records. Do not
display illustrative sample outcomes as real results.

## 6. Suggested Architecture

``` text
React + Vite Dashboard
          |
          v
FastAPI Application
          |
          +---- Repository Service
          |       +---- Git status and metadata
          |       +---- Scanner and finding extraction
          |
          +---- Task Planner
          |       +---- Deterministic priority rules
          |       +---- Ollama / local open-weight model
          |       +---- Structured output validation
          |
          +---- Policy Engine
          |       +---- Allowed task types
          |       +---- File and patch limits
          |       +---- Approved commands
          |
          +---- Execution Worker
          |       +---- Git worktree manager
          |       +---- Patch application
          |       +---- Test runner
          |       +---- Logs and timeouts
          |
          +---- Run and Report Service
                  +---- SQLite task history
                  +---- Diff metadata
                  +---- Markdown reports
```

### Component responsibilities

**Frontend** - Repository setup, queue management, run progress, diff
review, and reports. - Poll a run-status endpoint or use server-sent
events for live updates.

**FastAPI backend** - API endpoints, validation, orchestration, and task
state transitions. - Never trust a path, command, or task identifier
supplied by the client without validation.

**Repository service** - Git metadata, scanner execution, worktree
creation, diff extraction, and cleanup. - Detect unsafe repository
states before execution.

**Model adapter** - Communicates with Ollama. - Validates inputs and
structured outputs. - Supports switching models without changing the
rest of the application.

**Policy engine** - Applies the same rules before and after model
planning. - Enforces file scope, command allowlists, task budgets, and
approval requirements.

**Execution worker** - Performs bounded operations and captures logs. -
Maintains task state even when an operation fails.

**SQLite** - Stores repositories, scans, findings, tasks, runs, events,
and review decisions. - Avoid storing secrets or unnecessary source
content in logs.

loopback by default, validate request origins where applicable, and do
not expose the service publicly without an explicit security design.

## 10. Agent Workflow

### Step 1: Validate the repository

-   Resolve and validate the selected path.
-   Confirm it is a Git repository.
-   Record the current commit and branch.
-   Detect uncommitted changes.
-   Confirm the user has authorized scanning and the relevant file
    scope.

### Step 2: Scan

-   Run deterministic scanners.
-   Gather bounded evidence for each finding.
-   Deduplicate findings.
-   Save the scan result.

### Step 3: Rank

-   Calculate a deterministic baseline priority.
-   Ask the local model to summarize and classify candidate tasks.
-   Validate the model response.
-   Reject unsupported task types.
-   Prefer small tasks with clear verification.

### Step 4: Review and authorize

-   Display the proposed task and evidence.
-   Require approval before a code-changing attempt in the MVP.
-   Explain any risks and allowed file scope.

### Step 5: Create an isolated workspace

-   Create a worktree from the recorded base commit.
-   Confirm the expected branch and working-tree state.
-   Apply file and resource limits.

### Step 6: Plan and apply the patch

-   Supply only relevant, bounded context to the model.
-   Request a small patch with an explicit rationale.
-   Validate paths and patch scope.
-   Reject unexpected file changes.
-   Do not execute commands proposed freely by the model.

### Step 7: Verify

-   Run configured commands from an allowlist.
-   Capture exit codes, duration, and logs.
-   Apply timeouts.
-   Mark the task `passed`, `failed`, `not_run`, or `blocked` according
    to actual results.

### Step 8: Report

-   Produce the diff and run report.
-   Mark the task as requiring human review.
-   Let the user export, retain, or discard the patch.
-   Never merge, push, or deploy automatically in the MVP.

### Step 9: Cleanup

-   Preserve logs and reports.
-   Retain or remove worktrees according to user settings.
-   Ensure cleanup never deletes the original repository or user data.
-   Record cleanup failures.

## 11. Safety and Reliability Plan

RepoMoss can execute code, so safety is a core feature rather than an
optional extra.

### Required controls

-   Use an explicit repository allowlist.
-   Never operate on arbitrary paths supplied by model output.
-   Use Git worktrees and validate the base commit.
-   Detect and preserve pre-existing uncommitted changes.
-   Use an allowlist for test and validation commands.
-   Do not automatically run arbitrary install scripts, shell commands,
    or repository hooks.
-   Disable network access for execution environments by default where
    practical.
-   Set timeouts, output limits, file-count limits, and retry limits.
-   Prevent automatic access to `.env`, credentials, SSH keys, tokens,
    and other secrets.
-   Treat all repository content as untrusted input.
-   Validate model output before acting on it.
-   Require human approval before merging or applying changes to the
    main working tree.
-   Provide a cancellation mechanism and safe failure states.

### Threats to test

1.  A README containing instructions that attempt to override agent
    policies.
2.  A symlink that points outside the repository.
3.  A task that attempts to edit `.env` or another sensitive file.
4.  A generated patch that changes unrelated files.
5.  A test command that hangs indefinitely.
6.  A test that fails after a patch is applied.
7.  A repository with uncommitted user changes.
8.  A malformed model response.
9.  A Git operation that fails halfway through.
10. A cleanup operation that encounters a locked or modified worktree.

A Git worktree alone does not sandbox arbitrary code. For repositories
you do not trust, use a container or OS-level sandbox with restricted
filesystem and network access.

## 12. Evaluation Plan

Measure whether RepoMoss performs useful, verifiable maintenance---not
just whether the UI looks convincing.

### Functional metrics

-   Number of valid findings produced.
-   Percentage of findings accepted by a human reviewer.
-   Number of tasks attempted.
-   Patch application success rate.
-   Verification pass rate.
-   Number of tasks blocked by safety policies.
-   Number of unintended file changes.
-   Average run duration.
-   Local model latency and resource usage.

### Quality metrics

-   **Task precision:** proportion of surfaced findings judged genuinely
    useful.
-   **Patch acceptance:** proportion of attempted patches accepted by a
    reviewer.
-   **Verification success:** proportion of attempted tasks whose
    configured checks pass.
-   **Scope adherence:** proportion of attempts that change only
    expected files.
-   **Recovery quality:** whether failures are recorded and the original
    repository remains intact.

Track the denominator for every percentage. For example, report the
number of attempted tasks as well as the number of successful
verifications.

### Baseline comparison

Compare RepoMoss against a manual maintenance workflow on a small, fixed
set of seeded issues.

Record:

-   Time spent identifying issues manually.
-   Time spent making and testing the changes manually.
-   Time spent reviewing RepoMoss's patches.
-   Number of useful changes completed.
-   Number of incorrect or rejected changes.

Do not claim time savings until measured. If the agent takes longer than
manual work on a task, report that result honestly.

### Initial acceptance criteria

Suggested MVP acceptance criteria:

-   Successfully scan a known sample repository.
-   Produce at least three evidence-backed candidate findings from
    seeded examples.
-   Complete at least one supported maintenance task end to end.
-   Show the exact diff and actual verification output.
-   Preserve the original working tree.
-   Correctly record a failed verification.
-   Reject an attempt to modify a protected file.
-   Complete the core workflow without a remote model API.

These are targets to test, not claims about current performance.

## 13. Development Roadmap

### Phase 0 --- Scope and setup

**Deliverables** - Repository initialized. - Architecture and safety
boundaries documented. - Frontend and backend development environments
working. - Ollama/model availability checked on the target machine.

**Done when:** a health check can confirm backend, Git, database, and
local model availability.

### Phase 1 --- Repository scanner

**Deliverables** - Repository registration. - Git status and commit
capture. - TODO/FIXME scanner. - Markdown link checker. - Basic
documentation and test-coverage heuristics. - Findings list in the UI.

**Done when:** a sample repository produces repeatable, evidence-backed
findings.

### Phase 2 --- Local model planning

**Deliverables** - Ollama adapter. - Structured task-plan schema. -
Deterministic task prioritization. - Prompt-injection-resistant policy
boundaries. - Model errors and malformed responses handled safely.

**Done when:** the model can explain a supported finding and propose a
bounded plan without executing it.

### Phase 3 --- Isolated patch execution

**Deliverables** - Worktree manager. - Patch validation. - Command
allowlist. - Timeouts and output capture. - Verification state
machine. - Diff viewer.

**Done when:** a supported task can be attempted and verified without
modifying the original working tree.

### Phase 4 --- Reports and review

**Deliverables** - Task and run history. - Markdown report export. -
Human approval/rejection actions. - Worktree retention and cleanup
controls. - Clear failed, blocked, and review-required states.

**Done when:** a reviewer can reconstruct what the agent did and decide
whether to keep the patch.

### Phase 5 --- Deferred execution

**Deliverables** - Manual and scheduled run modes. - Configurable task
budgets. - Idle or scheduled maintenance window. - Cancellation and
recovery behavior. - Morning report.

**Done when:** a maintenance session can run on a schedule and produce a
report even when some tasks fail.

### Phase 6 --- Polish and submission

**Deliverables** - README and setup instructions. - Architecture
diagram. - Safety documentation. - Test results and limitations. -
Screenshots or a short demo video. - DEV post describing the problem,
implementation, open-AI rationale, and measured results. - Optional
agent session recording if available.

**Done when:** a new user can install the project, run the demo, inspect
the source, and understand the evidence supporting the claims.

-   Priority calculations.
-   Model-output schema validation.
-   Path validation.
-   Protected-file rules.
-   Task state transitions.
-   Report generation.
-   Timeout and failure classification.

### Integration tests

-   Scan a temporary Git repository.
-   Create and remove a worktree.
-   Apply a known patch.
-   Run a successful test command.
-   Run a failing test command.
-   Confirm the main working tree is unchanged.
-   Confirm logs and reports match the actual outcomes.

### End-to-end tests

1.  Register a sample repository.
2.  Run a scan.
3.  Review findings.
4.  Approve a supported task.
5.  Execute it in an isolated worktree.
6.  Inspect the diff.
7.  Verify the result.
8.  Export the report.
9.  Reject or discard the patch.
10. Confirm the original repository remains intact.

Use deterministic fake model responses in automated tests. Keep a
separate manual integration test for the real local model so that
ordinary tests do not depend on model availability.

## 16. Suggested Implementation Order

Work in small vertical slices so the project remains demonstrable
throughout development.

1.  Create the backend health endpoint and frontend shell.
2.  Add repository registration and Git metadata.
3.  Implement one deterministic scanner and render its findings.
4.  Add the rest of the initial scanners.
5.  Integrate Ollama for explanations and structured task plans.
6.  Add policy validation and task approval.
7.  Create an isolated worktree for a selected task.
8.  Support one narrow patch type, such as documentation repair.
9.  Run approved validation commands and capture results.
10. Add a diff viewer and Markdown report.
11. Add a second task type, such as a simple regression test.
12. Test safety boundaries and failure recovery.
13. Add scheduled execution only after manual runs are reliable.
14. Record a real end-to-end demo and document limitations.

Do not start with broad autonomous code editing. Prove the
scan-plan-execute-verify-report loop first.

## 17. Demo Script

Aim for a concise demo that shows actual behavior rather than a mockup.

### Scene 1 --- The neglected repository

Open a sample repository containing: - A missing README instruction. - A
simple uncovered edge case. - A TODO comment with enough context to
evaluate.

Explain that these small tasks are easy to postpone.

### Scene 2 --- RepoMoss scans

Register the repository and run the scanner. Show evidence-backed
findings and explain how the task priority was determined.

### Scene 3 --- Local AI proposes a bounded task

Show the local model's task plan, expected file scope, and verification
command. Approve the attempt.

### Scene 4 --- Isolated execution

Show the worktree or branch being created, the patch being applied, and
the configured test running.

### Scene 5 --- Evidence, not promises

Show the actual diff, test output, and final status. If the test fails,
demonstrate that the failure is recorded accurately.

### Scene 6 --- The morning report

Display the report and explain which tasks were completed, which need
review, and how the developer retains control.

Use a real recorded run. Clearly label any pre-recorded, simulated, or
illustrative content.

## 18. Open-AI Story for the Write-Up

The open-weight model should be central to the workflow, not an optional
chat panel.

Explain the concrete design choices:

-   **Local inference:** the model can analyze repository context on the
    developer's machine.
-   **Privacy:** source code need not be sent to a third-party inference
    provider.
-   **Model flexibility:** the model adapter separates model choice from
    repository and execution logic.
-   **Control:** prompts, task categories, risk policies, and budgets
    are configurable.
-   **Cost model:** no mandatory per-request inference API, while
    acknowledging hardware and electricity costs.
-   **Offline behavior:** after model and dependencies are installed,
    supported local tasks can run without internet access, provided
    their commands and dependencies do not require network access.

Be precise about the distinction between open-weight and fully
open-source software. Check the chosen model's license and
redistribution terms. Do not claim full offline operation until it has
been tested with network access disabled.

### Suggested write-up structure

1.  **The chore:** why routine repository maintenance gets postponed.
2.  **The idea:** an agent that tends a repository in small, controlled
    steps.
3.  **The implementation:** scanner, local model, policy engine,
    worktree, verification, and reporting.
4.  **The open-AI advantage:** local inference, privacy, model control,
    and cost characteristics.
5.  **The demo:** show the actual patch and test results.
6.  **Evaluation:** share measured successes, failures, review time, and
    limitations.
7.  **What comes next:** additional scanners, supported task types, and
    better recovery.

## 20. Definition of Done

RepoMoss is ready for an initial public demonstration when:

-   [ ] A user can install and run the application from documented
    instructions.
-   [ ] The user can register a local Git repository.
-   [ ] The scanner discovers known issues in a sample repository.
-   [ ] Findings include evidence and file paths.
-   [ ] A local open-weight model produces a structured, bounded task
    plan.
-   [ ] Policy checks run before a code-changing attempt.
-   [ ] A supported task can be attempted in an isolated worktree.
-   [ ] Only approved commands are executed.
-   [ ] The actual diff and verification output are visible.
-   [ ] Failed verification is reported as failure, not success.
-   [ ] The original working tree remains unchanged by the attempt.
-   [ ] The user can review and discard a patch.
-   [ ] A Markdown report can be exported.
-   [ ] Automated tests cover key policy and failure cases.
-   [ ] Offline claims are verified or clearly qualified.
-   [ ] The README explains limitations, safety controls, and hardware
    requirements.
-   [ ] The demo and write-up distinguish measured results from intended
    capabilities.

## 21. Future Extensions

Only consider these after the MVP works reliably:

-   Additional language-specific scanners.
-   Dependency-risk summaries without automatic upgrades.
-   Repository-specific maintenance policies.
-   Better historical deduplication of repeated findings.
-   Test-selection strategies for large repositories.
-   Optional isolated container execution.
-   Integration with issue trackers or pull requests, with explicit
    permissions.
-   Durable workflow execution for long-running tasks.
-   A maintenance history showing recurring issues and resolved
    patterns.
-   Model comparisons using the same fixed maintenance benchmark.

Each extension should preserve the core design: bounded tasks, isolated
execution, transparent evidence, and human control.

## 22. Final Product Positioning

**RepoMoss is not an autonomous developer that promises to fix
everything. It is a careful maintenance assistant that finds small
chores, attempts them in isolation, verifies what it can, and hands the
developer evidence-backed results.**

Its value is not the number of lines of code it generates. Its value is
reducing the mental overhead of remembering, prioritizing, and
completing routine maintenance without sacrificing control of the
codebase.

**The central promise:**

> Let RepoMoss handle the small, neglected chores---one verified task at
> a time---while you focus on building what comes next.
